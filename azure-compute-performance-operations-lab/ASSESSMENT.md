# 학습 효과 측정 가이드

이 문서는 “워크숍을 들었다”가 아니라 **운영 판단을 실제로 더 잘하게 되었는지** 확인하기 위한 사전·사후 평가입니다. 사전 평가와 사후 평가는 같은 문항과 같은 채점 기준으로 실시합니다.

## 1. 평가 운영

| 시점 | 시간 | 방식 | 사용 자료 |
|---|---:|---|---|
| 시작 전 | 15분 | 개인 평가 | Azure 문서·Portal 사용 금지 |
| 실습 중 | 세션별 | 팀 관찰 | Baseline, Analysis, GameDay 산출물 |
| 종료 직전 | 20분 | 개인 사후 평가 | 본인 팀의 결과만 참고 |
| 종료 후 | 10분 | 팀 발표 | Before/After evidence 표 |

개인 점수와 팀 점수를 분리합니다. 팀 산출물이 좋아도 개인이 원인과 근거를 설명하지 못하면 역량 습득으로 판정하지 않습니다.

## 2. 사전·사후 공통 문항

각 문항은 `답변`, `근거로 사용할 지표`, `다음 행동`을 함께 적습니다.

1. CPU 평균이 45%인데 p95 latency가 800ms라면 어떤 원인을 먼저 확인하겠습니까?
2. VMSS scale-out이 발생했지만 오류율이 계속 높다면 확인할 항목을 순서대로 쓰십시오.
3. 디스크 IOPS는 한계보다 낮지만 latency가 상승할 수 있는 이유는 무엇입니까?
4. VM SKU를 키우기 전에 반드시 기록해야 할 Before 지표 세 가지는 무엇입니까?
5. Health Probe가 실패한 VM은 `Running` 상태인데 트래픽을 받지 못합니다. 어디를 확인하겠습니까?
6. Autoscale의 scale-out 결정 시간과 새 인스턴스의 warm-up 시간을 어떻게 측정하겠습니까?
7. 두 변경안 중 하나가 p95를 20% 낮추고 다른 하나가 비용을 20% 낮춥니다. 어떤 추가 정보가 필요합니까?
8. 장애 복구를 선언하기 전에 어떤 조건을 얼마나 오래 관찰해야 합니까?
9. KQL 분석에서 모든 인스턴스의 문제와 한 인스턴스의 문제를 어떻게 구분하겠습니까?
10. 동일한 부하 테스트의 재현성을 확보하기 위해 고정해야 하는 변수를 세 가지 쓰십시오.

## 3. 실기 평가 시나리오

사후 평가에서는 다음 중 하나를 개인별로 수행합니다. 진행자는 원인을 알려주지 않습니다.

### 시나리오 A: CPU 병목

- 제공 정보: p95 상승, CPU·디스크·네트워크 시계열
- 수행: 10분 내에 가설과 확인할 쿼리 작성
- 통과: CPU만 높다고 결론 내리지 않고 최소 2개 지표의 시간 상관관계를 제시

### 시나리오 B: Scale-out 지연

- 제공 정보: 부하 시작, autoscale 결정, 인스턴스 Ready 시각
- 수행: decision latency, warm-up, SLO breach duration 계산
- 통과: 확장 정책의 문제와 애플리케이션 warm-up 문제를 구분

### 시나리오 C: 디스크 병목

- 제공 정보: IOPS, throughput, latency, queue depth 전후 값
- 수행: 디스크 tier 변경 여부와 검증 계획 작성
- 통과: IOPS 하나만 보고 결론 내리지 않고 변경·롤백 조건 포함

### 시나리오 D: Health Probe 장애

- 제공 정보: VM 상태, backend health, `/healthz`, `/readyz` 결과
- 수행: 영향 범위 파악 및 복구 순서 작성
- 통과: 서비스 복구 기준을 HTTP 200 하나가 아니라 Ready 인스턴스·오류율·p95로 정의

## 4. 채점 기준

### 개인 평가: 20점

공통 문항 10개를 각 0~2점으로 채점합니다.

| 점수 | 기준 |
|---:|---|
| 0 | 잘못된 답 또는 근거·다음 행동 없음 |
| 1 | 방향은 맞지만 지표, 시간축, 검증 방법 중 하나가 빠짐 |
| 2 | 원인 가설, 확인 지표, 검증 또는 다음 행동이 모두 있음 |

### 팀 산출물: 20점

| 영역 | 점수 | 통과 조건 |
|---|---:|---|
| 기준선 | 0~4 | 동일 부하·측정 창·정상 범위가 기록됨 |
| 병목 분석 | 0~4 | 최소 2개 지표와 시간 상관관계가 있음 |
| 튜닝 | 0~4 | Before/After, 비용, 롤백 조건이 있음 |
| Autoscale | 0~4 | decision, warm-up, recovery를 측정함 |
| 장애 대응 | 0~4 | 탐지·완화·복구·재발 방지가 연결됨 |

## 5. 전후 차이 판정

다음 세 조건을 모두 만족해야 “워크숍 목표 달성”으로 판정합니다.

1. 개인 사후 점수가 사전 점수보다 **20% 이상 향상**되고 12/20점 이상입니다.
2. 팀 산출물이 20점 중 **14점 이상**이며, 병목 분석과 튜닝 영역에서 각각 2점 이상입니다.
3. 실기 시나리오에서 원인 가설과 검증 계획을 **10분 안에** 작성하고, 최소 2개의 근거 지표를 사용합니다.

개인 사후 점수가 향상되지 않으면 진행자는 해당 참가자에게 실기 시나리오를 하나 더 제공하고, 답변에 포함된 지표·시간축·검증 단계를 함께 리뷰합니다.

## 6. Before/After 결과표

팀 발표에는 아래 표를 반드시 채웁니다. 숫자가 없으면 “개선됨”으로 인정하지 않습니다.

| 역량 | Before 증거 | After 증거 | 변화 |
|---|---|---|---|
| 성능 측정 | 평균 latency만 기록 | p50/p95/p99와 정상 범위 |  |
| 병목 분석 | 단일 지표 추측 | 2개 이상 지표의 시간 상관관계 |  |
| 튜닝 판단 | 큰 SKU로 변경 | 가설·동일 부하·롤백 조건 |  |
| 확장 운영 | 인스턴스 수 증가 확인 | decision·warm-up·recovery 측정 |  |
| 장애 대응 | Portal을 순서 없이 확인 | 탐지·영향·완화·복구 타임라인 |  |
| 운영 문서화 | 구두 설명 | 재사용 Runbook과 개선 백로그 |  |

## 7. 교육 품질 개선 루프

진행자는 다음 회차를 위해 익명 집계합니다.

- 사전 평균 / 사후 평균 / 향상률
- 문항별 정답률 변화
- 팀별 산출물 점수
- 가장 오래 걸린 실습 단계
- 재현되지 않은 테스트 수
- 참가자가 가장 어려워한 KQL 또는 운영 판단

향상률이 낮은 문항은 다음 회차에서 설명을 늘리는 것이 아니라, 해당 판단을 요구하는 **짧은 재현 실습과 채점 가능한 출력**을 추가합니다.
