# 진행자 가이드

## 1. 진행자의 핵심 메시지

이 워크숍의 성공 기준은 특정 Azure 기능을 많이 보여주는 것이 아닙니다. 참가자가 다음 질문에 근거를 들어 답하는 것입니다.

> “현재 병목은 무엇이며, 어떤 변경을 하면 SLO·비용·운영 리스크가 어떻게 달라지는가?”

## 2. 사전 준비 체크리스트

- [ ] 팀별 격리된 구독 또는 리소스 그룹
- [ ] 만료 태그와 비용 알림
- [ ] VM/VMSS, Load Balancer, Managed Disk
- [ ] Log Analytics Workspace와 VM Insights
- [ ] 샘플 HTTP 서비스와 `/healthz`, `/readyz`
- [ ] 부하 도구와 사전 정의된 부하 프로파일
- [ ] Azure Monitor Workbook 또는 시작 쿼리
- [ ] 장애 주입 스크립트와 복구 절차
- [ ] quota·지역 capacity 확인
- [ ] 종료 시 리소스 정리 스크립트

## 3. 진행 팁

### 기준선 단계

참가자가 곧바로 VM 크기 변경으로 가려 하면 멈추고, 먼저 “현재 정상 범위와 측정 창이 있는가?”를 확인하게 합니다.

### 병목 분석 단계

다음 순서로 질문합니다.

1. 사용자 영향은 무엇인가?
2. 영향이 시작된 정확한 시각은 언제인가?
3. 애플리케이션 지표와 플랫폼 지표가 같은 시각에 변했는가?
4. 다른 인스턴스에서도 동일한가?
5. 변경 또는 부하가 원인과 시간적으로 일치하는가?

### 튜닝 단계

큰 SKU로 즉시 변경하는 대신, 참가자가 다음 세 가지를 모두 쓰게 합니다.

- 변경 가설
- 기대하는 측정 변화
- 효과가 없을 때의 롤백 조건

### GameDay 단계

진행자는 원인을 직접 알려주지 않습니다. 단, 운영상 위험하거나 복구가 지연될 때는 다음 질문으로 유도합니다.

- 현재 영향 범위를 어떻게 제한할 것인가?
- 추가 변경 전에 어떤 상태를 보존해야 하는가?
- 복구되었다고 판단할 측정값은 무엇인가?

## 4. 권장 리뷰 질문

- 평균 CPU가 낮은데 p95가 높은 이유는 무엇일 수 있는가?
- VMSS 인스턴스 수를 늘리는 것이 항상 해결책인가?
- Health Probe가 너무 깊은 애플리케이션 검사를 수행하면 어떤 문제가 생기는가?
- scale-in 보호와 비용 사이의 trade-off는 무엇인가?
- 디스크 tier 변경으로 해결되지 않는 디스크 병목은 무엇인가?
- quota와 실제 지역 capacity를 왜 분리해서 생각해야 하는가?
- 장애 대응 후 어떤 자동화가 재발 방지에 가장 효과적인가?

## 5. 완료 기준

다음 조건을 만족하면 팀의 실습을 완료로 판정합니다.

- 기준선과 검증 부하가 재현 가능하다.
- 병목 결론에 최소 2개 이상의 상관 지표가 있다.
- 변경 전후의 동일 조건 비교가 있다.
- Autoscale 또는 장애 복구에 대한 시간 측정이 있다.
- 롤백 조건과 후속 조치가 문서화되어 있다.
- 비용·성능·안정성 trade-off를 한 문단으로 설명할 수 있다.

## 6. 종료 정리

1. 부하 발생기를 중지합니다.
2. 테스트용 경고와 공개 접근 규칙을 제거합니다.
3. 실습 리소스를 삭제하거나 중지합니다.
4. 비용 알림과 태그를 확인합니다.
5. 팀별 산출물을 수집합니다.
6. 참가자에게 “운영 환경에 적용하기 전 필요한 검증”을 한 가지씩 쓰게 합니다.
